# ADR 0009: Contracted Product Search and Explicit Development Fixtures

Date: 2026-10-05. Status: adopted under Csaba's approval of the issue #4 test proposal and implementation instruction.

## Context and decision

Issue #4 establishes frontend search cooperation against HTTP fixtures before issue #7 supplies the real Nest/PostgreSQL product operation. A is the accepted catalog hierarchy. Preserve the existing real health/readiness journey at `/`; expose search at `/search` without adding a routing dependency for two static entry paths. Shareable criteria and navigation behavior remain later issues.

`contracts/openapi.yaml` defines `GET /products?query=...`, the exact DTO, empty/success examples and stable recoverable error. Generate TypeScript and dereferenced Ajv schemas from that source. Both success and documented error JSON are parsed at the HTTP boundary; raw server prose is never UI text. The generator checks the new artifacts for drift alongside existing contracts.

RTK Query exclusively owns server products. The feature hook owns the editable input and 300 ms application delay. Blank input clears results immediately; only current, successful, non-fetching criteria can produce cards. Input edits, late responses and retry do not make an old query's products current. Preserve article-number leading zeros.

The typed message resource owns visible strings and locale-aware functions. Cards receive a narrow product/message contract and do not fetch or persist preferences. Semantic CSS roles own colors, spacing and control radii. Following the S71 review, currency conversion uses a local ISO minor-unit precision snapshot independently of Intl display rounding; Intl formats the converted amount. See the [snapshot provenance and refresh conditions](../../engineering/product-search-fixtures.md#currency-units). The introduction and search sit beside one another on desktop and stack on narrow screens. Light English is the initial presentation; selectors and preference persistence remain #5/#6. ADR-0003's broader i18next/provider choices remain proposed.

MSW intercepts HTTP only after explicit development opt-in. The `search-fixtures` serving mode opts in; an explicit false flag overrides it. Ordinary development does not automatically enable fixtures. Worker startup finishes before application rendering. Production's `import.meta.env.DEV` guard prevents startup even with a true flag, and removes the fixture module from the application bundle. The generated public MSW worker asset is inert unless explicitly registered. Its source is generated by the installed MSW CLI, then formatted with native Prettier.

Keep browser search configurations separate from the connected database suite. The existing Quality gate also runs fixture, production and disabled-mode browser cases. No coverage exceptions or lower thresholds are introduced. Bootstrap unit tests replace only the external browser-worker SDK boundary; actual Chromium cases verify the real worker registration and interception behavior.

## Alternatives and consequences

Directly returning fixtures from a feature hook would bypass the HTTP client and contract. Duplicating products in Redux would create competing owners. Enabling mocks solely because the environment is development would hide real integration failures. Adding themes, language selectors, URL criteria, filters or persistence now would expand the accepted slice.

This slice proves frontend cooperation, accessible current-query behavior and production mock exclusion. It does not implement the Nest product operation, SQL matching, authoritative stock or deployment. Fixture evidence is labelled in the UI. Before real backend integration, remove reliance on fixture assumptions through the existing contract rather than replacing the UI transport.

Review this decision when adding URL criteria, a real API, catalog localization, another currency source or account preferences. See the [approved test proposal](../../planning/issue-4-test-approval.md) and [Mikado plan](../../planning/issue-4-mikado-plan.md).
